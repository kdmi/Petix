# Boss NFT: как игроки будут клеймить, и что для этого нужно

Ресёрч от 2026-10-02. Опирается на код капсул (`api/_lib/nft*.js`, `contracts/DemoSlots.sol`, итоги 016), код выплат $PETIX (019), демо экспедиций (`expedition-demo/`) и срез прода на 2026-10-02: 1 288 кошельков с персонажами, 164 активных за 7 дней, 5 195 PvP-боёв за неделю.

Исходная идея владельца: отдельная коллекция, в которой игрок сам минтит NFT босса за три звезды; боссы открываются по очереди (например, раз в 4 дня), окно клейма по каждому боссу ограничено (например, 14 дней), чтобы каждый босс был отдельным инфоповодом.

---

## 1. Техника: как это сделать и что подготовить

### 1.1. Три способа выдать NFT

| | A. Минт игроком по ваучеру | B. Минт сервером (custodial) | C. OpenSea Studio, allowlist по стадиям |
|---|---|---|---|
| Как | Сервер подписывает ваучер (кошелёк, босс, срок, nonce); игрок зовёт `mint(voucher)` и платит газ | Серверный ключ с правом `mintTo(wallet, bossId)`; сервер платит газ, игрок только жмёт кнопку | Коллекция через SeaDrop, на каждого босса своя стадия с allowlist из кошельков, набравших 3★ |
| Что видит игрок | Транзакция в кошельке к верифицированному контракту (как на минте капсул) | Ничего не подписывает; NFT просто появляется, как выплата $PETIX | Страница минта OpenSea, allowlist обновляется руками |
| Нужен ETH у игрока | Да (~1e-5 ETH на RH chain, но ноль ETH = тупик) | Нет | Да |
| Риски | Красные баннеры в кошельках (та же причина, по которой владелец отверг ваучеры для выплат) | Горячий ключ с правом минта; ограничить только минтом, лимиты по боссу и по кошельку, отзыв ключа владельцем | Allowlist в SeaDrop обновляется через Studio; 10 стадий × ручная заливка списков; метаданные по боссу нужно всё равно отдавать самим |
| Стоимость газа | На игроке | ≈1e-5 ETH ≈ 2–3 ¢ за минт; 1 000 минтов ≈ $30 | На игроке + 10% комиссия OpenSea не применима (бесплатно) |

**Рекомендация: B.** Он совпадает с принятой философией «игрок ничего не подписывает» (решение по выплатам 2026-09-12), снимает требование иметь ETH и повторяет уже написанный паттерн выплат из `token-chain.js` (nonce-lock через CAS, реконсиляция по receipt). Вариант A оставить как опцию «забрать самому» для тех, кто принципиально хочет минтить своим кошельком; в первой версии не нужен.

### 1.2. Контракт `PetixBosses` (свой, не SeaDrop)

Минимальный ERC-721 на OpenZeppelin v5, по образцу `DemoSlots.sol`:

- `mintTo(address to, uint8 bossId)` — только `minter` (серверный ключ); `bossOf[tokenId] = bossId`; счётчик `mintedPerBoss[bossId]`.
- `setClaimWindow(bossId, opensAt, closesAt)` — только владелец; `mintTo` проверяет окно **on-chain**, чтобы серверный ключ физически не мог выдать NFT вне окна (защита от утечки ключа и от соблазна «добавить задним числом»).
- `maxPerWalletPerBoss = 1` on-chain.
- `tokenURI = baseURI + tokenId`, `contractURI = baseURI + "collection"`, ERC-2981 роялти 5%.
- Без `Enumerable` (газ) — владение читаем из `Transfer`-логов, как у капсул; но для боссов индекс владельцев нужен только для витрины «кто победил», можно читать лениво `ownerOf`.
- Без хранения трейтов on-chain: `bossOf` достаточно, остальное в метаданных.

Открытая эмиссия в окне: саплай каждого босса = число кошельков, взявших 3★ в окно. Редкость задаётся временем, а не числом. Это и есть механика «успей».

### 1.3. Бэкенд

1. **Серверная симуляция боя — обязательна до любого NFT.** Сейчас бой считается только на клиенте; `POST` с «3 звезды» подделывается за минуту. `engine.js` детерминирован по seed: сервер выдаёт seed при старте боя, клиент шлёт список ходов, сервер проигрывает их тем же движком и сам определяет звёзды. Это одновременно защита Points-наград.
2. Профиль кошелька: `expedition.seasons[seasonId].bosses[bossId] = { bestStars, attempts, claim: { tokenId, txHash, claimedAt } }` — через `updateWalletProfile`, как всё остальное.
3. `POST /api/expedition/claim { bossId }`: проверки — 3★ в серверной записи, окно открыто (по `economy-config`: `BOSS_OPEN_AT[i]`, `BOSS_CLAIM_UNTIL[i]`, рантайм из админки), ещё не клеймил; дальше очередь минта с nonce-lock, poll receipt, запись `tokenId`. Идемпотентность по `(wallet, bossId)`.
4. `GET /api/boss-nft/metadata/[tokenId]` — статичные метаданные по `bossOf`: имя босса, сезон, картинка (IPFS), трейты `Boss`, `Season`, `Claim wave` (первые 48 часов → «First wave»), `Earned by` (кошелёк, которому выдали). Картинки 10 штук готовятся заранее и кладутся в IPFS один раз; обновлять метаданные не нужно, ERC-4906 не нужен.
5. Крон синка владения не обязателен для v1 (NFT ничего не меняет в игре); если понадобится бонус держателям, индекс добавляется по образцу `nft-store`.
6. Админка: окна по боссам, пауза клейма (`BOSS_CLAIM_ENABLED`), счётчики минтов, ручной re-mint при упавшей транзакции.

### 1.3a. Контроль над метаданными после выдачи

Требование владельца: иметь возможность поменять облик уже выданных NFT. В предложенной схеме это решается так же, как у капсул, и ничего менять не нужно:

- **Метаданные живут у нас.** `baseURI` в контракте указывает на `https://petix.fun/api/boss-nft/metadata/`, а JSON собирается сервером из `bossOf[tokenId]`. Ничего не замораживается в IPFS, кроме самих файлов картинок, и ссылка на картинку тоже в нашем JSON. Чтобы сменить облик, достаточно положить новую картинку (новый CID в IPFS или blob) и поменять ссылку в конфиге босса; все токены этого босса меняются разом, без транзакций и без газа игрокам.
- **Как заставить витрины перечитать.** Кеш OpenSea обновляется либо refresh-API (на Robinhood Chain принимает, но не обещает), либо ончейн-событием `BatchMetadataUpdate(from, to)` от владельца — урок ревила капсул: событие надёжнее и стоит ~1,5e-6 ETH. Поэтому в контракте оставляем ERC-4906 и скрипт `emit-metadata-update.js`; смена арта = заменить файл, обновить конфиг, одна транзакция владельца.
- **Страховка от смены домена.** `setBaseURI` владельцем, как у капсул. Если переедем с petix.fun, токены не осиротеют.
- **Версионность, чтобы это не выглядело как подмена.** В JSON держать трейт `Art` со значением версии (`Season 1 · v1`, `v2`) и поле `image_original` с первой картинкой. Так коллекционер видит историю, а не внезапную замену, и мы можем объявить «обновили арт боссов» как инфоповод, а не оправдываться.
- **Про что помнить.** Бэкенд метаданных — единая точка отказа для всей коллекции: держать кеш в памяти инстанса и 503 с Retry-After, как сделано для капсул после атаки краулера на ревиле. И не отдавать в метаданных ничего, что может понадобиться скрыть (как `prompts` у персонажей).

Если захочется обратного, то есть «заморозить навсегда» для доверия коллекционеров, это тоже одна транзакция: `setBaseURI` на IPFS-папку с JSON и отказ владельца от ключа. Пока лучше оставить управляемыми.

### 1.4. Что подготовить вне кода

- 10 карточек NFT 1:1 из существующих 16:9 артов (босс + рамка + «3★» + «Season 1»); сейчас арты есть только для боссов 1 и 3.
- Название и символ коллекции (навсегда в контракте), баннер и описание для OpenSea, роялти.
- Кошелёк владельца контракта (холодный, как у капсул) и свежий минтер-ключ с минимальным ETH (~0,02 ETH хватит на ~2 000 минтов).
- Деплой и верификация на Blockscout, репетиция на testnet 46630.

## 2. Игровая и вирусная механика

**Что работает в идее:**

- **Редкость через время** честнее и понятнее, чем через саплай: «NFT получили все, кто был достаточно хорош в эти две недели». Нет гонки за кнопку минта, нет ботов, нет «не успел купить».
- **Доказательство силы и навыка.** Лимит ходов у босса фиксирован и одинаков для всех (решение 2026-10-02), поэтому три звезды значат одно и то же для каждого кошелька: отряд достаточно прокачан и бой сыгран аккуратно (HP ≥ 50%). NFT босса = «я прошёл его хорошо», и это сравнимо между игроками.
- **Инфоповоды раскладываются сами:** открытие босса, «половина окна прошла, N кошельков уже взяли», «последние 48 часов», «окно закрыто, выдано N». Это 3–4 поста на босса, 30–40 на сезон, без выдумывания контента.
- **Сет из 10** даёт долгую цель коллекционеру: публичная страница «ваш сет 6/10», трейт `Season 1 Complete` для тех, кто собрал все десять, и отдельный пост в конце сезона со списком полных сетов.
- **Вторичка как усилитель:** тот, кто не успел, может купить NFT босса у того, кто взял. Это создаёт цену у навыка и даёт сильным игрокам доход, а нам роялти. Поэтому NFT стоит делать передаваемыми, а не soulbound; «кто заработал» фиксируется в метаданных.

**Где нужна аккуратность:**

- **Маленькие тиражи поздних боссов выглядят мёртвыми**, если показывать их как «сминчено 4». Подавать как достижение: «Crown Bear повержен четырьмя кошельками», список с никами. Малое число здесь плюс, если так и рассказывать.
- **Усталость от FOMO.** Десять окон подряд с «последним шансом» через месяц перестают работать. Чередовать тон: открытие = интрига про босса, закрытие = итоги и герои, а не угрозы.
- **Повторные попытки стоят 5–8k Points на поздних боссах.** Это сильный сток Points (хорошо для экономики), но для игрока должен быть виден прогресс: «лучший результат 2★, лимит ходов 23, ваш рекорд 25» прямо в модалке, чтобы попытка ощущалась как приближение, а не лотерея.
- **Один клейм на кошелёк и босса.** Мультиаккаунты получают несколько NFT, но каждому нужен прокачанный отряд и Points на попытки, поэтому фарм NFT через сибилов дорогой; дополнительно можно требовать капсулу на кошельке, как для вывода, но это отсечёт новичков, которым первый босс как раз и адресован. Для боссов 1–2 капсулу не требовать, для 3+ можно.

## 3. Риск: игроки не успеют прокачаться

Прогноз (`expedition-demo/project-stars.js`) на реальных активных кошельках: каждый сохраняет свой текущий темп PvP-боёв (медиана 29 в неделю), выигрывает 55%, +200 XP за победу по кривой из `battle-progression.js`, XP идёт в сильнейших петов. Ячейка: доля активных, берущих 3★ не реже чем в половине попыток / доля, выигрывающих хотя бы раз.

Эффект заметен на первых боссах: раньше прокачанный отряд получал более жёсткий лимит и 3★ на боссе 1 брали 23% активных, теперь 73%. На поздних боссах картина почти не изменилась: там лимит не главный барьер, игрокам просто не хватает силы отряда, чтобы победить с половиной HP.

Что это значит для расписания «босс раз в 4 дня, окно 14 дней» (босс N открывается в день 4(N−1), окно закрывается в день 4(N−1)+14):

- Боссы 1–3: окна закрываются в дни 14–22, 3★ к тому моменту у 55–80% активных. Первые NFT получает большинство играющих: это правильно для входа в сезон, редкость начинается дальше.
- Боссы 4–5: окна закрываются в дни 26–30, 3★ у 35–42%. Хорошая середина.
- Боссы 6–7: окна закрываются в дни 34–38, 3★ у 10–19%. Жёстко, но это «элитный» хвост.
- Боссы 8–10: окна закрываются в дни 42–50, 3★ у 5–20%, босс 10 около 10%. Половина активных их даже не побеждает. Для 3★ придётся отряд L12+, то есть игроки, которые играют с июля и покупают энергию.

Сам по себе хвост с 5–10% не проблема, если это осознанная «корона сезона». Проблема в другом: **прогноз сделан по текущему темпу боёв, а он ограничен 3 боями в день.** Игрок, который хочет NFT шестого босса, упирается не в умение, а в календарь: XP приходит фиксированно, в бою с боссом XP не выдаётся (решение 017). Три рычага, которые это смягчают, без изменения правил боя:

1. **Адаптивная каденция вместо фиксированных 4 дней.** Следующий босс открывается, когда хотя бы 25% активных кошельков победили предыдущего (любой звёздностью), но не раньше 4 и не позже 8 дней. По прогнозу это даёт примерно 4-4-4-5-5-6-6-7-7 дней, сезон растягивается с 40 до ~50 дней, а окна поздних боссов попадают туда, где 3★ достижимы для 15–25%, а не 5%.
2. **Окно клейма 14 дней для боссов 1–5 и до конца сезона для 6–10.** Инфоповод «последний шанс» остаётся у всех, но для хвоста он один общий: «сезон закрывается, последняя неделя на корону».
3. **Покупка энергии как честный ускоритель.** Магазин энергии уже на проде (пакеты 1/150, 3/400, 5/500). Прогноз при удвоенном темпе боёв сдвигает таблицу примерно на одну колонку влево, то есть 3★ по боссу 8 к дню 28 получают ~20% вместо 11%. Это и сток Points, и понятный ответ на «не успеваю»: не «плати за NFT», а «играй больше».

Чего делать не стоит: раздавать XP за боссов (превращается в эмиссию через ферму, решение 017) и ослаблять par для поздних боссов (тогда 3★ перестанет означать мастерство, и NFT обесценится).

Отдельно про удачу: лимит ходов фиксирован, и у отряда целевого уровня 3★ выходит примерно в 45% побед с полным HP, у отряда на тир выше почти всегда. Для игрока это 2–4 платные попытки на NFT. Это нормальная цена, но её нужно показывать заранее: «средний игрок вашего уровня берёт 3★ с третьей попытки».

## 4. Итоговые предложения

1. **Коллекция `Petix Bosses`, свой ERC-721, минт сервером, окно клейма on-chain.** Один NFT на кошелёк и босса, передаваемый, роялти 5%, саплай по боссу = число успевших. Метаданные отдаёт наш сервер (облик можно менять после выдачи, см. 1.3a), картинки в IPFS.
2. **Сначала серверная симуляция боя**, потом всё остальное. Без неё NFT и Points-награды подделываются.
3. **Расписание сезона 1:** первый босс открыт в день 0; следующий открывается по правилу «25% активных победили предыдущего, но 4–8 дней»; окно клейма 14 дней для боссов 1–5 и до конца сезона для 6–10; сезон закрывается, когда закрылось окно 10-го босса, ориентир 50–55 дней.
4. **Контент-календарь на босса:** открытие (кто он, арт, сколько HP и щитов), середина окна (N кошельков уже взяли, топ по ходам), за 48 часов до закрытия, итоги (выдано N, лучшие результаты). Плюс конец сезона: полные сеты.
5. **В интерфейсе:** таймер окна на карточке босса и в модалке, лучший результат и лимит ходов рядом, кнопка Claim только при 3★ и открытом окне, после клейма ссылка на OpenSea и карточка для шаринга (как у PvP-боёв).
6. **Аналитика с первого дня:** доля победивших и взявших 3★ по боссу среди активных, число попыток до 3★, Points, сожжённые на попытках. Это позволит крутить каденцию по правилу из п.3 на реальных числах, а не по прогнозу.
7. **Что оставить на сезон 2:** допуск к минту своим кошельком (вариант A), бонус держателям сета в игре, продажа «пропуска на попытку» без Points.

## 5. Задача со звёздочкой: вторая монета

Короткий ответ: **второй fungible-токен запускать не советую**, а то, чего хочется от «монеты», можно получить двумя способами без второго токена. Если всё же делать, ниже условия, при которых это не выглядит скамом.

**Почему второй токен сейчас вреден.** $PETIX запущен две недели назад, ликвидность одна. Второй токен от того же проекта делит внимание и ликвидность, а для внешнего наблюдателя «два токена у одной игры за месяц» — это паттерн, по которому распознают схему, независимо от механики. Пояснять придётся каждому.

**Вариант 1 (рекомендую): «монета» = сами NFT боссов как ERC-1155.** Вместо ERC-721 с уникальными tokenId сделать ERC-1155, где `id = bossId`, а баланс = число медалей этого босса. Внутри босса медали взаимозаменяемы, их можно копить, дарить, продавать по штуке, собирать «по одной каждого». Это даёт ощущение валюты и рынка (цена медали шестого босса против первого), но это коллекционный предмет, а не токен с кривой. Минт тот же серверный, окна те же. Минус: OpenSea показывает 1155 менее нарядно, чем 721, и «у меня 3 медали первого босса» требует механики получения второй медали (например, 3★ в каждом из окон повторных сезонов).

**Вариант 2: $PETIX как ресурс крафта.** Клейм NFT требует не только 3★, но и сжигания N $PETIX (или Points, которые 1:1). Это создаёт сток для основной монеты, а не вторую монету; держателям $PETIX это понятная польза. Риск: порог в $PETIX отсекает тех, у кого нет вывода (без капсулы 36 ч). Можно брать Points: механически то же самое, но без ончейн-шага.

**Вариант 3: «Boss Essence», отдельный ERC-20, если очень хочется.** Условия, без которых это читается как скам:

- эмиссия только через игру: каждая победа над боссом даёт фиксированное количество Essence по звёздам, формула публичная и в контракте, минт только с серверного минтера в рамках on-chain лимита на сезон;
- ноль преминта, ноль командной доли, ноль продажи: команда получает Essence только побеждая боссов со своих кошельков, и это видно в цепи;
- единственное применение внутри игры: сжигание на клейм NFT босса (например, 3★ даёт достаточно на свой NFT, 2★ не хватает, добираешь у других игроков) и на будущие крафты;
- никакого лаунча на Pons, никакой кривой, никакого «листинга»: ликвидность появляется только если игроки сами создадут пул, и проект это не продвигает;
- фиксированный конец эмиссии (сезон) и публичный дашборд: сколько выпущено, сколько сожжено, сколько у кого.

В таком виде Essence это игровой ресурс с рынком, как руда в MMO, а не монета для спекуляции. Но даже так это новый контракт, новая страница на эксплорере и новый вопрос в каждом чате. Ценность для игры та же, что у варианта 2, а стоимость объяснений выше. Поэтому порядок предпочтений: 1 (если нужна «монетность») → 2 (если нужен сток) → 3 (только если есть отдельная причина иметь торгуемый ресурс навыка).
